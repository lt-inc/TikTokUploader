# Загрузка в TikTok: диагностика и варианты для пилота

Проверено 28 октября 2026. Исходная версия TikTokUploader: `5f1c627`.
Пользователь подтвердил ошибку при загрузке видео; логов и TikTok-сессии для
воспроизведения нет. Исправления ниже проверены локально, но успешная загрузка
в TikTok и устранение конкретного отказа `30411` не подтверждены.

## Что делают репозитории

Terex управляет расписанием, готовыми MP4, метаданными, попытками и историей.
Он отправляет команду через RabbitMQ и временный URL файла отдельному Python
worker из TikTokUploader. Расширение браузера передаёт сессию аккаунта; worker
проверяет владельца и использует приватные веб-запросы TikTok Studio.

Основной путь: создать проект → получить upload credentials → `ApplyUploadInner`
→ передать части файла → `CommitUploadInner` → подписать и отправить публикацию
→ подтвердить настоящий пост в Studio. Это адаптация autotok 2.0.1, а не
официальный Content Posting API. Браузер используется для подписи, помощи с
авторизацией и проверки поста; сама передача файла реализована HTTP-запросами.

В истории репозитория уже есть изменения nonce, параметров Studio, кодирования
SigV4 и Chrome TLS/HTTP2 для борьбы с `30411`. Нет оснований обещать, что ещё одна
перестановка заголовков гарантированно исправит отказ.

## Подтверждённые дефекты и изменения

- Проверка ограничения на upload endpoints не учитывала HTTP 429 без ожидаемого текста. Теперь
  учитываются HTTP-статус и структурированный `CodeN`, включая компактный JSON.
- `Retry-After` терялся. Теперь учитываются секунды и HTTP-дата; минимальная
  пауза остаётся 30 минут. Повторы управляются Terex, без циклов ожидания в worker.
- Пауза относилась к одному видео. Теперь worker сохраняет зашифрованную паузу
  для аккаунта: следующие задачи не начинают сетевую работу с TikTok до её конца.
  Сопутствующее изменение Terex отличает `tiktok_account_cooldown` от реального
  отказа TikTok и не расходует бюджет неудач видео на простое ожидание.
- Перед Chrome-запросом cookies сворачивались в словарь по имени. Это теряло
  domain/path и могло подменять одноимённые cookies. Теперь используется общий
  CookieJar; принятые обновления и удаления cookies сохраняются для следующего
  HTTP-запроса. Подписанный Apply-запрос не следует редиректам.
- Диагностика upload failure содержит этап, HTTP-статус, код провайдера и
  задержку. Тела ответов и текст сетевых исключений в этот лог не попадают:
  там могут быть временные ключи загрузки или реквизиты прокси.

Повтор после начавшейся финальной публикации по-прежнему запрещён при неизвестном
результате. Rate limit после финального send не означает, что видео безопасно
загрузить повторно. Unit-тесты и локальный HTTP-сервер проверяют эти инварианты,
но не совместимость приватного протокола с текущим TikTok.

## Как проверить исправление на stage

1. Сначала развернуть сопутствующий патч Terex для `tiktok_account_cooldown`,
   затем ревизию TikTokUploader через существующий процесс `lt-inc/k3s`.
   В рамках исследования инфраструктура не менялась, видео не отправлялись.
2. Выбрать одну публикацию без неопределённой предыдущей попытки. Если предыдущая
   попытка могла отправить final POST, сначала проверить её в TikTok/Terex.
3. Выполнить один приватный технический тест. Сохранить SHA образа и строку
   `upload failed ... stage=... status=... provider_code=... retry_after_seconds=...`,
   если она появится. Не экспортировать cookies, ключи или полный HAR.
4. Если получен `30411`, дождаться паузы. Проверить обычную ручную загрузку
   из браузера на том же сетевом маршруте. Если ручная работает, а HTTP-worker
   нет, это аргумент в пользу несовместимости реализации веб-протокола;
   если не работает и ручная, проверять аккаунт/сессию/маршрут.
5. Успех технического теста — настоящий post ID и правильная видимость.
   Для эксперимента с просмотрами затем нужен отдельный публичный пост:
   приватная публикация охват не проверяет.

По одному тексту `Too many requests` нельзя различить HTTP 429, отказ VOD
`30411` и лимит публикаций. Код `30411` не имеет найденной официальной публичной
таблицы причин. Смена IP или обход проверок не включены в исправление.
Отдельная проблема обработки 429 в проверке identity не менялась: данный патч
сосредоточен на подтверждённом пользователем этапе загрузки видео.

## Собственное решение без платных сервисов

Добавлен экспериментальный режим `TIKTOK_UPLOAD_MODE=studio`. Он использует
локальный Phantomwright/Chromium, уже входящий в Docker-образ. Не нужны
подписки, API-ключи сервисов публикации или TikTok developer app.

В этом режиме файл выбирается в форме TikTok Studio, а штатный JavaScript сайта
сам получает upload credentials, передаёт файл и подписывает публикацию.
Это устраняет необходимость вручную воспроизводить эти запросы в HTTP-клиенте.
Ограничения самого TikTok и необходимость действующей сессии остаются.

Worker явно задаёт описание и приватность, получает настоящий media ID из
ответов загрузки и проверяет содержимое финального запроса. Перехватчик браузера
сохраняет реальный creation ID и вызывает durable checkpoint Terex непосредственно
перед отправкой. Разрешён один финальный запрос: автоматические повторы сайта
блокируются. Редиректы изменяющих запросов блокируются на уровне Chromium CDP,
поскольку обычный Playwright route не перехватывает повторный запрос после 307.
После ответа браузер закрывается, а пост
проверяется существующей процедурой Studio reconciliation.

Для включения на stage:

```text
TIKTOK_UPLOAD_MODE=studio
```

Остальные настройки сессии, worker и маршрута сохраняются. По умолчанию остаётся
`http`; переключение режима выполняется явно перед новой попыткой. После
неопределённого результата нельзя переключить режим и заново отправить то же
видео без проверки существующего поста. Настройку окружения нужно добавить
в существующий deployment в `lt-inc/k3s`; этот репозиторий здесь не менялся.

Это собственный прототип с локальными проверками, а не подтверждённая работа
на вашем TikTok-аккаунте. Изменение селекторов, неожиданная модалка или неподдержанная
структура publish payload останавливает попытку. При login/challenge требуется
пройти существующий Browser verification до новой попытки. Для первого запуска
нужен технический приватный ролик; для проверки просмотров — затем публичный.

Проверки: `TIKTOK_STUDIO_BROWSER_TESTS=1 pytest -q` — 41 passed, включая пять
сценариев в настоящем Chromium на локальном стенде. `compileall` и
`git diff --check` прошли. В Terex полный `main-be: go test ./... -count=1`
прошёл на Go 1.26 с отдельным PostgreSQL 17. Реальная загрузка в TikTok ещё
не выполнялась: публичный адрес стенда требует Basic Auth, сессии в этой среде нет.

Исследован бесплатный проект
[wkaisertexas/tiktok-uploader](https://github.com/wkaisertexas/tiktok-uploader),
SHA `1cea92dd4c815dbd5127ee4b3a0a7b6fabbaa5f0` (MIT). Он использует Playwright
и веб-интерфейс. Его код целиком не подключён: в проверенной версии ошибки
выбора приватности проглатываются, а после ошибки Post выполняется повторный
клик. Для Terex это нарушило бы требования к приватности и отсутствию дублей.

[Anything API / Notte](https://anything.notte.cc/docs) создаёт браузерные
автоматизации, но готовый проверенный TikTok publishing endpoint не найден;
его облачная тарификация не соответствует требованию собственного бесплатного
решения. Для текущего прототипа достаточно имеющегося браузерного runtime.
